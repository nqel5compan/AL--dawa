# تقرير المرحلة 0 — الفهم والجرد والقرارات (AL-DAWA-v2)

> أُنفّذت كل المراحل بناءً على توجيه صاحب المشروع («نفّذ المراحل كلها») — هذه الصفحة توثق فهم المنتج، جدول الفجوات مع المرجع، والتعارضات التي اتُّخذ بشأنها قرار افتراضي **للمراجعة**.

## 1) المنتج بصفحة واحدة (بكلمات المهندس)

**ما المنتج:** منصة «الدواء | Al Dawa» توصل العميل في سوهاج **للفحص الصح في الوقت الصح** وتتابعه بعد النتيجة. المنصة ليست جهاز كشف — الفحص (أشعة/عينة/تحليل) هو ما يكشف، والطبيب هو من يشخّص، والمنصة تنظّم وتربط وتتابع لحظيًا.

**الأطراف الأربعة وصلاحية كل طرف:**
- **العميل:** يجيب أسئلة صحته → يرى «فحوصاتك الوقائية» (المطلوب/اللي اتعمل/الجاي) مع السبب والمصدر وتاريخ آخر اعتماد → يطلب فحصًا من معمل فيأخذ **رقم طلب + QR** → يستلم النتيجة بشرح بسيط → يرى رأي الطبيب وخطة المتابعة وتذكيراتها. لا يرفع شيئًا بنفسه افتراضيًا (`ALLOW_PATIENT_UPLOAD` مغلق).
- **المعمل (+ مشرف):** يرى الطلبات لحظيًا (رقم/كود أو بحث برقم الموبايل) → يتحقق من صاحب الطلب → يرفع تقريرًا أو أكثر أو يُدخل القيم → يراجع ويضغط «تأكيد وإرسال» → يرى متى فتح العميل النتيجة → يعالج التصحيحات (إصدار جديد، الأصل محفوظ). اختلاف الاسم ⇒ **IdentityHold**: الإرسال متوقف حتى مراجعة مشرف المعمل. يرى طلباته فقط (`labId` في كل استعلام).
- **الطبيب المشرف:** صندوق واحد مرتب بالأهمية (حرج ← تغيّر مهم ← بانتظار رد ← متأخر ← عادي) مع SLA؛ يرى الحالات المسندة إليه فقط (بموافقة DOCTOR_SHARE)؛ يكتب الرأي وخطة المتابعة التي تتحول لتذكير؛ لا يعدّل نتيجة المعمل بل يطلب تصحيحها.
- **الإدارة:** تدير المعامل والأطباء والمراكز والباقات والإعدادات وتوقف أي حساب فورًا (`tokenVersion`) — ترى **أرقامًا مجمعة فقط**، لا نتائج مرضى ولا آراء أطباء.
- **المسؤول الطبي (بجوار الإدارة):** يعتمد البروتوكولات وقواعد القيم الحرجة حصرًا (DRAFT→IN_REVIEW→APPROVED→RETIRED) — لا يظهر للعميل إلا المعتمد.

**ما لا تفعله المنصة أبدًا:** لا تقول «عندك/مفيش سرطان» ولا تنفي المرض بنتيجة طبيعية؛ لا توصية إلا من قواعد مخزنة كبيانات معتمدة من المسؤول الطبي (الذكاء الاصطناعي يشرح فقط)؛ لا نسب احتمال إصابة؛ لا نفس التحاليل للجميع؛ لا تحاليل أورام في الدم للفحص لدى الأصحاء (بقرار طبي فقط)؛ لا قيمة طبية في أي إشعار/حدث/لوج/رسالة صادرة؛ صياغة «قد تكون مؤهلًا…» لا «ستتحمى».

**السيناريوهات السبعة (لحظية بلا تحديث صفحة):** ① طلب العميل يظهر للمعمل فورًا ② تأكيد المعمل يصل للعميل والدكتور معًا + إشعار «نتيجتك جاهزة» ③ فتح العميل يظهر للمعمل ④ رأي الدكتور يصل للعميل فورًا ⑤ قيمة حرجة ⇒ تنبيه 123 للعميل + تصعيد أول صندوق الدكتور + إشعار المعمل بلا قيم ⑥ التصحيح يبلغ العميل والطبيب ويعلّم الرأي القديم «يحتاج مراجعة» ⑦ سحب الموافقة يقطع استقبال المعمل والطبيب فورًا.

**معيار النجاح:** طبيب وموظف معمل غير تقنيين ينجزون كل مهامهم من أول استخدام دون شرح (تُقاس e2e Playwright بزمن وصول فعلي بالثواني).

## 4) خطة المراحل المنفذة وأخطارها

المراحل 1→11 نُفذت بالترتيب (الأساس والأمان ← البيانات والأدوار ← الموقع العام ← الحسابات ← الفحوصات والمعمل ← تجربة العميل ← الطبيب والمسؤول الطبي ← الإدارة ← الذكاء الاصطناعي ← اللحظي ← النشر والقبول). الأخطار الرئيسية المعالجة: سباقات الاستلام/الاستخراج (أقفال شرطية)، تعدد نسخ الخادم (Redis pub/sub + outbox)، منع الغلط الطبي (IdentityHold + قواعد معتمدة + إقرار فقط للنتائج الموثقة)، الخصوصية (تشفير + HMAC + redactPii + بلا قيم في الصادر)، الإغلاق الفوري (tokenVersion + فحص الموافقة عند كل تدفق). المتبقي قبل الإطلاق: مراجعة قانونية لسياسة الاحتفاظ، اعتماد طبي حقيقي، مزود SMS/بريد إنتاجي، وملء أسماء المراكز.
